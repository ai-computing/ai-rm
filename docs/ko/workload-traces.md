# 워크로드 트레이스와 이종 NPU 환경의 현재 위치

[문서](README.md) · [English](../workload-traces.md) · [end-to-end 실행](e2e.md)

공개 운영 트레이스 5개로 실제 LLM 트래픽의 모양(요청 도착, 프롬프트·응답 길이, 프롬프트 앞부분 공유)을 정리하고,
각 트레이스가 지금의 이종 NPU 환경에 무엇을 요구하는지 적습니다. 2026-10-19에 전체 파일로 분석했습니다.

재현: rm-bench에서 `rm-bench traces fetch` 후 `python3 tools/trace_atlas.py ~/.cache/rm-bench/traces`를 실행하면 아래 수치가
JSON으로 나옵니다. 재생은 `rm-bench e2e --scenario trace-<이름>`.

### 트레이스별 성격

- **Azure 대화: 균형 잡힌 채팅.** Poisson에 가까운 도착, 1천 토큰대 프롬프트, 백여 토큰의 응답. 토큰 수로는 prefill이 84.5 %지만
  요청당 시간으로는 decode가 큽니다. RNGD에서 잰 토큰당 17 ms로 보면 중앙값 응답은 decode에 약 2.2초이고, prefill은 우리가
  처리할 수 있었던 200–400토큰 프롬프트에서 약 0.2초였습니다.
- **Azure 코드: prefill과 burst.** 요청의 86 %가 prefill 위주이고 출력 중앙값은 13토큰. 가장 붐비는 1초에 평균의 26배가 몰립니다.
  꼬리 지연은 burst가 정합니다.
- **BurstGPT: 하루 주기와 두 가지 워크로드.** 61일 동안 가장 한가한 시간과 붐비는 시간이 약 12배 차이. API 호출(요청의 90 %)은
  짧고(출력 p50 26–40) 대화 호출은 깁니다(229–240). 긴 프롬프트가 긴 응답으로 이어지는 유일한 트레이스(순위 상관 0.58).
- **Mooncake 대화: 긴 문맥, 멀리 떨어진 재사용.** 프롬프트 중앙값 6.9K, p99 85K 토큰. prefix 블록의 37 %가 반복되지만 반복의
  절반은 약 2분 뒤에 옵니다. LRU 블록 캐시로 27 % 적중하려면 Llama-8B KV 기준 약 1 TB가 필요하고, 4–70 GB로는 약 4 %입니다.
- **Mooncake tool-agent: 긴 문맥, 즉시 재사용.** 같은 길이에 블록 재사용 55 %, 대부분 바로 반복됩니다. 4 GB 캐시로 이미 27 %,
  17 GB로 33 % 적중합니다.

## 우리 이종 NPU 환경의 한계

2026-10-19 기준: 스케줄 가능한 이종 노드 1대(RNGD 3, ATOM 4). RNGD+ATOM PD는 KONI/Llama-8B, context 512, 배치 최대 8로 검증
(RNGD 1 + ATOM 2–3에서 최고 135–177 tok/s). end-to-end 실행은 RNGD prefill + RNGD decode, `shm` 전송.

| 한계 | Azure 대화 | Azure 코드 | BurstGPT | Mooncake 대화 | Mooncake tool |
|---|:-:|:-:|:-:|:-:|:-:|
| 컴파일 길이 S=512 | 32 % 처리 | 22 % | 62 % | 0 % | 0 % |
| decode 용량 (decode 인스턴스 1개, 배치 ≤ 8) | **병목** | — | 피크에 병목 | 병목 | — |
| prefill 용량, 오토스케일 없음 | — | **병목** (burst) | **병목** (하루 피크) | 병목 | 병목 |
| ATOM 메모리 (카드당 15.7 GiB) | B16 불가 | — | — | **긴 KV를 ATOM에 둘 수 없음** | 같음 |
| KV 전송 (shm은 S 버퍼 전체 복사, P2P는 512에서만 검증) | 작음 | 작음 | 작음 | **병목** | **병목** |
| prefix 캐시·KV 계층 없음 | — | — | — | 재사용 37 % 손실 | **재사용 55 % 손실** |

### 한계 상세

1. **시퀀스 길이.** 컴파일된 그래프와 검증 경로가 모두 context 512(`seqLen` 256–512)입니다. 대화의 1/3, 코드의 1/5만 처리하고
   Mooncake는 처리하지 못합니다. Azure 대화의 85 %에는 S=2048, Mooncake의 93 %에는 32K가 필요합니다. 그래프는 shape마다
   미리 컴파일하므로 새 S마다 RNGD와 ATOM 양쪽에서 컴파일·검증이 새로 필요합니다.
2. **decode 용량.** decode 인스턴스 하나가 배치 단위로 처리합니다. Azure 재생에서 클라이언트 TPOT이 서버의 4–5배였던 것은
   겹친 요청이 decode를 기다렸기 때문입니다. ATOM B8이 이미 15.7 GiB 중 약 15.0 GiB를 써서 B16은 메모리 작업이 먼저입니다.
   대략 계산하면 Azure 대화의 평균 수요는 출력 약 1,170 tok/s로, B8 PD 한 묶음 최고치(135–177 tok/s)의 7–9배입니다. 512를 넘는
   요청을 빼고도 노드 하나(RNGD 3 + ATOM 4)로는 부족합니다(짧은 문맥 처리량 기준 추정).
3. **burst와 하루 주기.** 풀은 손으로 배치한 고정 Deployment이고 늘리고 줄이는 장치가 없습니다. cold start는 약 1분(prefill 62초,
   decode 18초, 그래프는 미리 컴파일)이라 초 단위 burst(Azure 코드 26배)는 남는 용량으로만 흡수할 수 있고, BurstGPT의 하루 주기에서는
   밤에 대부분의 용량이 놉니다.
4. **ATOM 메모리와 긴 문맥.** Llama-8B의 KV는 토큰당 128 KiB로 Mooncake 중앙값 프롬프트에 0.9 GB, p99에 11 GB입니다. ATOM에는
   가중치 옆에 둘 자리가 없어 긴 문맥 decode를 ATOM에 둘 수 없습니다. RNGD(48 GB, 가중치 뒤 약 32 GB)도 KV 전체로 약 25만 토큰,
   긴 요청 몇 개 분량입니다.
5. **KV 전송.** `shm` 경로는 S 크기 버퍼 전체를 복사합니다(S=512에서 67 MB, p90 약 111 ms). Mooncake 중앙값 길이로 늘리면 요청당
   1초를 넘습니다. RNGD→ATOM 직접 P2P는 context 512에서 정확성만 검증했고(KONI, Qwen 0.5–3B) 아직 기본 서빙 경로가 아니며,
   큰 전송은 측정하지 않았습니다.
6. **prefix 재사용 없음.** PD 게이트웨이는 요청마다 처음부터 prefill합니다. prefix 캐시도, KV offload 계층도(npu-offload는 KV가 아니라
   MoE expert를 옮김), EPP의 캐시 인지 라우팅도 없습니다. tool-agent 트래픽은 RNGD HBM에 들어가는 4 GB 캐시로 블록 27 %를 적중할 수
   있습니다.
7. **서빙 인터페이스.** 스트리밍 없는 `/v1/completions`만, 고정 생성 길이, greedy decoding. 스트리밍이 생기기 전에는 표준 벤치마크
   도구(GuideLLM, MLPerf LoadGen)가 TTFT를 볼 수 없습니다.
8. **효율.** host-staged 경로에서 측정한 전체 MFU 상한은 0.15–4.5 %, 3.9–120 GFLOPS/W로 목표 341 GFLOPS/W에 못 미칩니다. 위의 모든
   한계가 카드당·와트당 goodput도 낮춥니다.
9. **노드 하나.** 분석 시점에 etri-esc8000-e11(RNGD 2, GPU 2)은 cordon 상태였고 GPU/GB10 노드는 쓸 수 없어 scale-out과 RNGD+GPU
   조합을 시험하지 못했습니다.

### 트레이스별 첫 번째 지렛대

| 트레이스 | 먼저 할 것 |
|---|---|
| Azure 대화 | S=2048 그래프, decode 배치와 decode 인스턴스 증설(P:D 1:N) |
| Azure 코드 | RNGD에서 더 긴 prefill 그래프와 chunked prefill, burst용 여유 용량 또는 빠른 scale-up |
| BurstGPT | 대기열 길이 기반 오토스케일(KEDA 설치되어 있음), 컴파일 산출물을 데워 두어 cold start 단축 |
| Mooncake 대화 | RNGD 긴 문맥 그래프, P2P KV 전송, 먼 재사용을 위한 호스트 DRAM KV 계층 |
| Mooncake tool-agent | RNGD HBM prefix 캐시와 EPP의 캐시 인지 라우팅 |

트레이스와 현재 측정에서 나온 가설입니다. 다음 실험에서 트레이스별로 `rm-bench` 재생(SLO 아래 카드당 goodput)으로 확인합니다.
